# Расчётная спецификация прототипа

Версия 0.1 · Дата: 2026-08-04
Статус: **прототипная упрощённая модель.** Прод использует полный трёхдвижковый расчёт с блендингом из `Sales/Wizard/wizard_brd_v3_unified.md`. Задача этой спецификации — числа, «примерно реалистичные» для теста с sales (требование PO), при полной честности арифметики: формулы настоящие, ставки — provisional.

## 1. Ставки (Ratenkatalog v0-prototype)

Базовая ставка выведена обратным ходом из вашего реального расчёта: Referenzprojekt R-02 v2 даёт KG 300+400 = **1.685,49 €/m² BGF R oberirdisch нетто** при MFH, EH 40 + QNG, Holz-Modulbau. Снимаем модификаторы (÷1,06 ÷1,03):

```
K_base (MFH, GEG-Mindeststandard, KG 300+400) = 1.545 €/m² BGF (R) netto
Split внутри блока: KG 300 = 76,2 % · KG 400 = 23,8 %   ← факт Referenzprojekt R-02
```

Все коэффициенты ниже — **provisional (⚙)**. Решение по калибровке (04.08.2026, принято PO-делегированием): **прототип запускается на этих значениях**, калибровка не блокирует. Протокол ревизии — раздел 6.

Значения не выдуманы: базовая ставка выведена обратным ходом из реального расчёта Referenzprojekt R-02, сплит 300/400 — факт того же файла, ставки UG и коэффициент BGF S — из практики модульного строительства, множители типов — по относительным уровням BKI-таблиц. Точность ±10–15 % на коэффициенте второго порядка не выходит за доверительный интервал индикативного оффера (±10…25 %), поэтому запуск оправдан. Каждое значение ⚙ выводится в интерфейс как источник (DC-21), поэтому подмена калиброванным значением не потребует переделки UI.

**Множитель принадлежит оси, а не «типу здания» (D-11 v2, R-13).** Единого селектора `Gebäudetyp` в продукте нет; в расчёте остаётся таблица множителей, но каждая строка приписана к своей оси и к своему уровню:

| Ось | Уровень | Что задаёт |
|---|---|---|
| `Gebäudeform` | Building | конструктивную сложность объёма |
| `Nutzungsart` | Usage Segment | уровень оснащения по назначению |
| `Belegungs-/Barrierefreiheitsprofil` | Usage Segment | надбавки доступности и оснащения |
| `Benchmarkprofil` | Usage Segment | знаменатель ведущей метрики и справочник сравнения |

Здание с `2..n` сегментами не имеет одного множителя назначения — ставка считается по сегментам. Таблица ниже задаёт значения; в реализации каждое из них читается с той сущности, которой ось принадлежит.

| Множители формы и назначения ⚙ | EFH/ZFH 1,10 · DH/REH 1,05 · MFH 1,00 · Mischnutzung 1,04 · Senioren 1,06 · Wohnheim/Internat 0,95 · Hotel 1,15 · Büro 1,05 · Gewerbe 0,80 — все provisional, калибровать по BKI-таблицам. Первые три — `Gebäudeform`; остальные — `Nutzungsart` сегмента |

### 1.1 Маржа и Risikozuschlag — принятые провизорные значения

Закрыто 04.08.2026 (делегировано PO). Структура — по D-01/D-02; **числа провизорные, ревизия по разделу 6.** В интерфейсе всегда помечены как provisional, конфигурируются в S6 без правки кода.

| Маржа (скрыта от клиента, D-01) | Ставка ⚙ |
|---|---|
| `Marge Eigenleistung` — то, что All3 производит и монтирует сама | **12 %** |
| `Marge Fremdleistung` — пропускаемое через себя (Tiefgarage, Außenanlagen, Erdarbeiten, Abbruch) | **6 %** |

Обоснование уровней: в немецкой практике генподрядная надбавка «Wagnis und Gewinn» лежит в однозначных–низких двузначных процентах; у собственного заводского производства маржа выше, у транзитных субподрядов — вдвое ниже. Соотношение 2:1 важнее абсолютных значений: оно и есть то, что нельзя выразить одной ставкой.

| Risikozuschlag-драйвер (виден клиенту, D-02) | База | Ставка ⚙ |
|---|---|---|
| Baugrundgutachten liegt nicht vor | KG 320 | **+4 %** |
| Grundwasser / Abdichtungsklasse offen | KG 320 | **+3 %** |
| Statik nicht geprüft | KG 300 | **+2 %** |
| Beengte Baustelle / Kranstellung unklar (`C0.22`) | KG 300 | **+3 %** |
| Bestandsgebäude / Abbruchumfang unklar (`C0.20`) | KG 200 | **+5 %** |
| Denkmalschutz / Erhaltungssatzung offen | KG 300 | **+3 %** |

Принцип калибровки драйверов: ставка соответствует **стоимости худшего правдоподобного исхода по этой позиции**, а не среднему. Драйвер существует, чтобы его снял присланный документ (D-02); заниженная ставка лишает механику смысла, завышенная делает оффер неконкурентным. Сумма активных драйверов ограничена **12 % от Bauwerk** — выше этого порога проект не индикативный, а требующий предварительного изучения (система выдаёт предупреждение, а не молча суммирует).

## 2. Цепочка расчёта варианта

```
для каждого включённого здания g:
  Bauwerk_g = [ BGF_R_ober_g × K_base × F_typ × F_gk × F_energie
              + BGF_S_g × K_base × F_typ × F_gk × F_energie × f_S
              + UG_g ]  × F_region      ← F_region = 1,00, пока флаг D-15 не включён

  UG_g:  vollausbau → BGF_UG × (1100 + 90×parking)
         ab_decke   → BGF_UG × (350 + 90×parking)
         kein_ug    → 0

Bauwerk = Σ Bauwerk_g

KG 700:  Modus vereinfacht → тотал НЕ меняется, блок показывается 70/22/8
         Modus echt        → + Bauwerk × 12 %
KG 500/200/100/600/800:  по D-07 (ручные суммы / Erfahrungswert / auf Anfrage)

Risikozuschlag: Σ активных драйверов, каждый = % × своя KG-база; отдельной строкой
Rabatt:         % на итог или по группам; после всего
Kennzahlen:     Leitkennzahl из Benchmarkprofil сегмента (D-11 v2):
                  €/m² WFL nach WoFlV  |  €/m² NUF nach DIN 277
                + всегда: €/m² BGF oberirdisch · €/WE (если жильё)
                Gemeinschaftsfläche — ОТДЕЛЬНЫЙ тип площади; её включение
                в знаменатель Benchmarkprofil объявляет явно (DATA-005)
```

**Агрегация по комплексу (D-14, пересмотрено 04.08.2026 по R-11).** Суммы (стоимость, BGF, WFL, NUF, WE) складываются по включённым зданиям; **все удельные метрики пересчитываются от сумм, никогда как среднее из средних**. Bauzeit комплекса = `max(start_i + dauer_i)`, не сумма. Доверительный интервал — взвешенный по стоимости зданий.

```
€/m² BGF oberirdisch = Gesamtkosten / Σ BGF oberirdisch  ← база сравнения с BKI, клиенту показывается
€/m² сегмента = Kosten(Segment) / Fläche(Segment)  ← знаменатель из Benchmarkprofil сегмента
                Wohnen  → WFL nach WoFlV
                Büro/Handel/Gewerbe → NUF nach DIN 277

Interne Bezugsgröße = Σ WFL + Σ NUF   ← ТОЛЬКО Internal Workspace.
   Запрещено: любой Output Profile, сравнение с BKI, вывод «x % unter Median».
   Обязательная подпись: «keine normative Fläche · WFL nach WoFlV + NUF nach DIN 277».
```

**Почему объединённая величина исключена из клиентских выдач.** WFL измеряется по WoFlV, NUF по DIN 277 — разные нормативные основания. Их сумма не является нормативной площадью, поэтому не может служить знаменателем клиентской ставки и не сопоставима ни с одним справочником. Формализованная взвешенная `Interne Mischkennzahl` в v0.5 не реализуется: требуется утверждённая формула и веса (R-11).

**Leitkennzahl определяется Benchmarkprofil сегмента (D-11 v2, R-13).** Не типом здания. Профиль явно объявляет знаменатель и его норматив:

| Benchmarkprofil | Знаменатель |
|---|---|
| BKI EFH/ZFH · DH/RH · MFH · Seniorenwohnen | `€/m² WFL nach WoFlV` |
| BKI Wohnheime | `€/m² WFL nach WoFlV`. **Gemeinschaftsfläche — отдельный тип площади**; если профиль включает её в знаменатель, подпись обязана называть состав полностью, например `€/m² WFL nach WoFlV + Gemeinschaftsfläche` — молчаливое расширение WFL запрещено (DATA-005) |
| BKI Büro/Verwaltung · Hotels · Gewerbebau | `€/m² NUF nach DIN 277` |

Здание с `2..n` сегментами единой Leitkennzahl **не имеет** — показываются сегментные. Bauzeit-фактор привязан к `Gebäudeform`, а не к прежнему смешанному «типу» (⚙ инженеры; маппинг на 3 группы методологии v1.1 — временный fallback).

Порядок операций фиксирован: модификаторы мультипликативны **до** регионального фактора, надбавки и скидка — аддитивны **после**.

Упрощения прототипа, о которых sales говорим прямо (G-подсказка): смешанное использование считается по единой ставке (NUF влияет только на Kennzahlen); третий уровень KG в прототипе только для KG 300 как статическое разбиение ⚙.

### 2.1 Точность и округление (CALC-007)

**Хранится точное значение, округляется только показ.** Ни одна производная величина не берёт на вход отображаемое число: скидка считается от точной суммы, удельные — от точных сумм и точных площадей, KG-разбиение — от точного итога. Правило «сначала округлили, потом посчитали» — источник расхождения, при котором «точное значение» в расшифровке не совпадает с собой.

| Величина | Шаг показа | Метод | Префикс `≈` |
|---|---|---|---|
| Деньги | 1.000 € | «к ближайшему», половина вверх | если показ ≠ точного |
| Удельные ставки | 1 €/m² | «к ближайшему», половина вверх | если показ ≠ точного |
| Проценты | 0,1 процентного пункта | «к ближайшему» | если показ ≠ точного |
| Срок | целый месяц, если интервал целый; иначе 0,5 месяца | «к ближайшему» | если показ ≠ точного; рядом обязательна абсолютная дата |

> **Исправлено 05.08 по вердикту аудитора.** Прежняя редакция снимала префикс `≈` со срока.
> Это было расширением отклонения от R-26 на требование **CALC-007**, которого PO не отклонял:
> отклонён формат месяцев, а не видимость округления. Точная длительность Haus A —
> `7,283` месяца, показ `7,5`, значит префикс обязателен. Основание — `decisions.md` **D-17**.

Каждое значение несёт `displayPrecision` и `displayRoundingMode`, и оба входят в снапшот расчёта (`data-model.md` §5.2, §5.9) — поэтому показ воспроизводим, а не пересчитывается заново при каждом открытии.

**Раскрытие обязательно и различается по поверхности.** В интерфейсе — префикс `≈` плюс постоянно доступная расшифровка `Gerundet auf <Schritt>; exakter Rechenwert <Wert>`. В PDF и письме — пометка `gerundet` непосредственно у метрики **и** повтор шага округления и точного значения в связанной обязательной сноске; одного из двух элементов недостаточно.

Ставки в drill-down не округляются сверх шага таблицы: иначе сумма строк перестаёт сходиться с итогом, а сходимость проверяется тестом (`data-model.md` §9, пункты 26 и 33).

### 2.2 Разграничение базы и опций (CALC-013)

Подземный этаж — место, где двойной учёт возникает сам собой: надбавка за паркинг сидит внутри ставки UG, и та же работа предлагается опцией. Границы объявлены явно:

| Scope Item | Кому принадлежит | Что входит |
|---|---|---|
| `UG.Konstruktion` | база, если `UG ≠ kein_ug` | конструктив и фундамент подземного этажа |
| `UG.Ausbau` | база при `vollausbau`; опция `UG-Ausbau` при варианте только по перекрытию | отделка подземного этажа |
| `TG.Zuschlag` | база, если `has_parking = true` | вентиляция, покрытие пола, ворота |

Множества базы и опций **не пересекаются**: при `vollausbau` опция `UG-Ausbau` недоступна, потому что её объём уже в базе, и интерфейс называет причину, а не просто гасит контрол. При включённом `has_parking` опция `Tiefgaragen-Zuschlag` недоступна по той же причине. Любое пересечение, не покрытое явным разбиением одной суммы (`CostAllocationRelation`, `data-model.md` §5.4), **блокирует расчёт** до разрешения — это не предупреждение.

### 2.3 База применения регионального фактора (CALC-009)

Фактор выключен по умолчанию (D-15). До активации показывается формула и **поимённый перечень затронутых строк** — иначе эффект в несколько процентов от итога возникает из ниоткуда.

```
затронуто:      KG 300 · KG 400 · UG (блок Bauwerk целиком)
не затронуто:   KG 100 · KG 200 · KG 500 · KG 600 · KG 700 · KG 800
                Risikozuschlag — надбавки считаются от уже пересчитанных KG-баз,
                поэтому отдельно на них фактор не накладывается (двойной учёт)
                Rabatt — применяется после всего
```

В драйверах затрат фактор присутствует строкой **всегда**: при выключенном состоянии — с суммой, которую он добавил бы, и пометкой `nicht aktiviert`. Состояние флага входит в снапшот отправленного оффера, поэтому «почему у прошлого оффера другая цифра» отвечается снапшотом, а не памятью.

### 2.4 Идентичность сценария (CALC-002)

Каждый блок, показывающий сумму, ставку, интервал или срок, несёт идентификаторы своего происхождения: `scenarioId`, `variantVersionId`, `calculationRunId`, `runPurpose`, `rulesetVersion`, `benchmarkSnapshot`, `engineVersion` и отметку времени в зоне IANA. Два числа, отличающиеся друг от друга, обязаны либо явно принадлежать разным прогонам, либо считаться дефектом. Без этого «± 19 % на одном экране и ± 22 % на другом» не отличить от ошибки — а отличить нужно за секунды при клиенте.

## 3. Интервал точности

Ровно по `t0-fallback-rules.md` §5–5.1: база ±10 %, + Σ Δ подставленных параметров с учётом источника (abgeleitet — полная Δ, manuell — Δ/2, bestätigt/Dokument — 0), потолок ±35 %, зоны ≤15 / ≤25 / >25.

## 4. Bauzeit

Ровно по `bauzeit-calculator-methodology-v1.1.md`:

```
dauer_g   = max(3; (5 + (BGF_ober_g − 1000)/750) × F_typ_zeit × F_gk_zeit)
F_typ_zeit: EFH/RH 0,85 · MFH 1,00 · Wohnheim 1,15
F_gk_zeit:  GK1 0,90 · GK2 0,95 · GK3 1,00 · GK4 1,05 · GK5 1,15
start_g   = planung(3, тумблер) + index_g × stagger(3)
projekt   = max(start_g + dauer_g);  округление 0,5 мес.; даты от Baubeginn
Фазы: Rohbau 30 % / Ausbau 70 % (для Gantt в презентации)
```

Параметры модели (planung, stagger, min) редактируются в S6, в оффер идут только использованные значения. Срок подписывается «ab OKBP» — база сравнения зафиксирована в D-03.

KG 800 (если включена): `Bauwerk/2 × Finanzierungszinssatz × (planung+dauer)/12` — информационная строка.

## 5. Протокол ревизии ⚙-значений

Калибровка не блокирует прототип, но обязана произойти по расписанию — иначе провизорные значения незаметно станут «правдой».

| Когда | Что делаем | Кто |
|---|---|---|
| **До пилота** (обязательно) | Прогнать 5–10 пар «индикативный оффер ↔ финальная Kostenberechnung» из архива через движок и сравнить: базовая ставка, WFL/BGF, доля BGF S, размеры WE | PO + инженеры |
| **Первые 2–3 месяца пилота** | Shadow-режим (`metrics.md` §7): каждый проект считается системой и экспертом; расхождение >15 % — триггер калибровки конкретного коэффициента | инженеры |
| **Ежеквартально** | Ревизия Kennwert против нового издания BKI + переоценка ставок маржи | финансы + инженеры |
| **По событию** | Проигранная сделка с причиной «цена» → разбор драйверов риска этого оффера | руководитель продаж |

Техническая поддержка: `Ratenkatalog` версионирован (`gültig_ab`, data-model §5/M-3), поэтому калибровка **не перепишет историю** — уже отправленные офферы остаются воспроизводимыми на своих ставках. Это и есть причина, по которой запуск на провизорных значениях безопасен.

| Referenzprojekt R-02 | обратная проверка ставки: при EH 40 + QNG расчёт должен воспроизводить ≈ 1.685 €/m² BGF R oberirdisch × BGF Bauantrag; WFL 665,75 → €/m² WFL nach WoFlV ≈ 2,4–2,6 тыс. |
| Referenzprojekt R-03 | 3 «здания»-крыла как одно Gebäude, UG-Parkgarage 2.377 m² ab_decke+parking, NUF-коммерция в EG → проверка смешанного использования и Kennzahl €/m² NUF nach DIN 277 |

Числа сверяются при сборке фикстур; расхождение теста и ручного счёта > 1 € — баг округления.

**Три строки выше — внутренняя доказательная база, а не тестовые данные.** Они показывают, откуда выведена базовая ставка, и по этой причине сохранены (решение Batch 2: реальные ссылки допустимы во внутренних документах решений, не публикуются, PII удалены). Тесты движка на них **не запускаются**: тестовые данные обязаны быть синтетическими, иначе прогон тестов распространяет реальные цифры проектов по логам и снимкам.

### 6.1 Синтетические контрольные примеры — на них идут тесты

Источник значений — `docs/audit/synthetic-fixtures.md`. Площади подобраны круглыми, чтобы арифметика проверялась без остатка, а `Gebäudeklasse` намеренно оставлена в состоянии `Prüfung erforderlich`, а KG 500 — в покрытии `unknown`: фикстура обязана воспроизводить блокирующие правила, а не удобный путь.
