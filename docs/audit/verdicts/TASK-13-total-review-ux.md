## Контекст от PO — главный критерий всего ревью

Дословный комментарий владельца продукта (обращён к автору прототипа, то есть к Claude; тебе он передан как рамка оценки):

> «Сейчас этот продукт напоминает очень утилитарный технический интерфейс, а я хочу, чтобы он был лёгким и интуитивно понятным, будто это не огромный громоздкий конфигуратор, а интернет-магазин с выбором опций. Поэтому мне и нравилось множество механик и компонентов из дизайн-системы, которые ты почему-то проигнорировал.»

Это не пожелание тона — это критерий приёмки. Каждую находку взвешивай против него: приближает ли исправление продукт к «выбору опций с видимыми последствиями» или оставляет его «заполнением налоговой формы». Витрина `all3-design-system.html` уже несёт нужные механики (призрак-превью, кольцо готовности, плитки опций с ценой, карточки фасадов, следующий шаг); PO прямо говорит, что ему нравились именно они — и что прототип их не взял.

Рамку ограничивает правило 27 (README §7): из магазинов и игр берём **структуру, не декор** — очки, бейджи, конфетти, звуки запрещены; тест любой механики — «не приближает оффер к отправке или точность к цели → её не существует». «Лёгкий как магазин» достигается ясностью выбора и мгновенным откликом, а не украшением.

## Объект и роли

Объект ревью — **прототип** (`src/**`) и то, как он потребляет дизайн-систему. По §2-bis это штатная перекрёстная проверка: прототип — зона Claude, значит, ты здесь второй инструмент в полном смысле, без оговорки задания № 12.

- На время ревью Claude **не трогает `src/**`** — работает только в `tools/` и `docs/`. Объект неподвижен.
- Дефекты в `src/**` ты **не правишь** — называешь адресом (`файл:строка · класс дефекта · что видно`), исправляет Claude по вердикту.
- Дефекты и недостающие компоненты в `design-system/**` — твоя зона: правь и дополняй сразу, фиксируя в отчёте. Прототип подключает `design-system/components.css` через `@import`, поэтому твои исправления доедут до него без изменений в `src`.

## Жёсткие данные для старта

Измерение от 06.08: **из 282 классов системы прототип использует 78, не использует 204.** Воспроизвести:

```bash
python3 - <<'EOF'
import re, pathlib
css = pathlib.Path('design-system/components.css').read_text(encoding='utf-8')
declared = sorted(set(re.findall(r'\.(a3-[\w-]+)', css)))
src = '\n'.join(p.read_text(encoding='utf-8') for p in pathlib.Path('src').rglob('*.tsx'))
unused = [c for c in declared if c not in src]
print(len(declared), len(declared) - len(unused), len(unused))
EOF
```

Среди неиспользуемых — ровно те механики, о которых говорит PO: `a3-okc-tile` (DC-40 · плитки опций с ценой на плитке), `a3-fgrid`/`a3-f-*` (DC-20 · карточки фасадов), `a3-modal` (DC-33), `a3-savechip` (DC-30), `a3-notecard` (DC-43), `a3-hinweis` (DC-7), `a3-tour-*` (DC-14), `a3-heroband`, `a3-ann` (карточки Annahmen), `a3-mode-card`, `a3-cmp` (сравнение вариантов), `a3-mailcard`, `a3-empty-*`, `a3-form-field`/`a3-form-error`.

Два предупреждения к этому числу:

1. **Использование ≠ правильное использование.** Класс из известного класса дефектов «почти правильно»: корневой класс взят, дочерняя структура из перечня `Classes:` — нет, и компонент тихо разваливается. Все 78 используемых проверяются против структурных контрактов, не по факту вхождения строки.
2. **Не всё неиспользуемое — долг.** Часть классов служит только витрине. Итогом должно стать трёхчастное разбиение: «обязан быть в прототипе» / «уместен позже» / «только витрина».

## Программа ревью

### A. Сценарный проход в браузере

`npm run dev` (или `npm run build && npm run preview`). Пройди золотой путь глазами продавца: список Opportunities → карточка → анализ документов → конфликты → параметры проекта → создание Option → главы 1–9 конфигуратора → правая панель → Vergleich → Export. Обязательные вариации: оба режима (intern / Präsentation), оба языка (DE / EN), `prefers-reduced-motion`, ширины 1280 / 1440 / 1920 и узкая ~1100.

Классы дефектов те же, что в задании № 12 (наложение, неотличимые состояния, смысл только цветом, скругления/градиенты, оранжевый вне разрешённого, U+202F, боковая прокрутка) **плюс** уровневые:

- тупик: экран, с которого непонятно, куда дальше (нарушение DC-27 «один следующий шаг»);
- необъяснённая блокировка: элемент недоступен и не говорит почему (правило 12);
- действие без отклика: клик, после которого ничего видимо не изменилось;
- жаргон: подпись, которую продавец не произнесёт клиенту вслух;
- пропавший контекст: экран требует помнить то, что было три экрана назад.

### B. Компонентный аудит используемого

Для каждого из 78 используемых классов: структура по контракту `design-system/components-core.md` и перечням `Classes:` в `components.css`; семь состояний данных (правило 30) там, где компонент несёт данные; клавиатура и ARIA (правило 22); зона нажатия 44×44 (правило 23); формат чисел и U+202F (правило 7). Особо — места, где Claude собрал «похожее на компонент» из утилит рядом с готовым классом системы: это двойники, их надо назвать.

### C. Разрыв с витриной — adoption-лист

Из 204 неиспользуемых выбери и приоритизируй **топ-10 к немедленному принятию**: класс/механика → экран и место в прототипе → что даёт по критерию PO → адрес контракта. Отдельно: механики «магазина», которых нет ещё и в витрине (карточка опции с изображением, сводка-«корзина» выбранного, сравнение опций бок о бок до фиксации) — их ты вправе спроектировать и добавить в систему сразу, в своей зоне, с контрактом и витринным образцом. Каждая обязана пройти тест правила 27.

### D. Оценка UX/UI и юзабилити

Структурированная оценка по экранам (список, карточка Opportunity, каждая глава конфигуратора, панель, Vergleich, Export). Для каждого экрана шесть измерений:

1. решений на экран — сколько вопросов экран задаёт одновременно;
2. кликов до последствия — сколько действий до видимого изменения цены;
3. язык — термины каталога или человеческие формулировки следствий;
4. прогресс и следующий шаг — видно ли, где я и что дальше;
5. безопасность эксперимента — обратимость, призрак-превью, Undo;
6. плотность — воздух листов витрины или стена таблиц.

Вердикт по каждому экрану: «магазин» / «между» / «налоговая форма» + три главных исправления. Оценка «нормально» без названной причины результатом не является — как и в № 12, результат это либо адрес, либо причина, по которой дефекта здесь быть не может.

## Формат отчёта

Файл `docs/audit/verdicts/codex-total-review-260806.md`. Первая строка:

```
РЕВЬЮ: дефектов K (в DS исправлено M, к Claude N) · adoption-лист: 10 · экранов «магазин»: X из Y
```

Дальше: таблица дефектов `адрес · класс дефекта · что видно · что сделать · зона (DS — сделано / src — Claude)`, ранжированная по тяжести; раздел «Оценка UX/UI» по экранам; adoption-лист с приоритетами; раздел «чего я проверить не могу» — его закроет вторая сторона.
