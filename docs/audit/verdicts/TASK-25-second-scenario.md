## Повод: у прототипа один рабочий сценарий из восьми

`DEMO-0001` (Musterprojekt Nordfeld) проработан целиком; остальные семь Opportunities честно помечены «im Prototyp nicht ausgearbeitet» и на клик отвечают заглушкой. Для теста с продавцами этого мало по трём причинам:

1. **Один сценарий не показывает вариативность.** Продавец видит конфликт WFL, два здания и клинкерный фасад — и не может проверить, ведёт ли инструмент себя разумно на офисном здании, на комплексе из трёх домов, на проекте без конфликтов вовсе.
2. **Демонстрация одного кейса выглядит как демонстрация мокапа.** Второй сценарий, ведущий себя по-другому, — это доказательство, что работает механика, а не один заготовленный экран.
3. **Наши собственные инварианты проверены на одном наборе чисел.** Правило 39 (удельные от сумм, `Bauzeit = max(start + dauer)`), агрегация комплекса, сегментные ставки — всё это сегодня подтверждается одной фикстурой. Второй набор — независимая проверка арифметики, а не только UI.

## Что нужно

Полный набор синтетических данных для **одной новой Opportunity**, отличающейся от первой по существу, а не по названию. Предлагаемый профиль (можешь обосновать другой, но отличие должно быть содержательным):

- **комплекс из трёх зданий**, из них одно офисное — тогда работает запрет единой Leitkennzahl при `2..n` сегментах (D-11 v2) и агрегация «от сумм, не среднее из средних» (правило 39);
- **конфликтов в документации нет**, зато **две открытые группы покрытия** — путь, где итог остаётся промежуточным по другой причине, чем в первом сценарии;
- **Baugrundgutachten есть** — риск D-02 не возникает, и продавец видит, как выглядит проект без надбавок;
- **сдвинутые старты** зданий, чтобы `Bauzeit = max(start + dauer)` считался нетривиально.

### Состав поставки

| Блок | Что нужно |
|---|---|
| Opportunity | id, имя, страна, город, owner, стадия, дата встречи, число зданий и документов |
| Здания | по каждому: id, форма, класс, энергостандарт, BGF R/S надземная и подземная, WFL, NUF, NRF, единицы, этажи |
| Документы | имена файлов, число страниц, статус разбора; хотя бы один с версиями |
| Расписание | по каждому зданию начало/конец, планирование проекта; **старты сдвинуты** |
| Покрытие | состояние каждой KG; две группы оставить `unknown` |
| Контрольные величины | итог комплекса, итог каждого здания, ведущая ставка каждого сегмента, `Bauzeit` комплекса — **посчитанные по `calculation-spec.md`**, а не назначенные |

**Контрольные величины — главное в поставке.** Они станут юнит-тестом: расхождение движка с ними будет release-блокером ровно так же, как для первого сценария (правило 32). Приведи арифметику каждого значения — цепочку от `K_base` через модификаторы, как это сделано в `synthetic-fixtures.md` для `DEMO-0001`.

## Границы

- **D-21 в силе:** ни одного реального адреса, номера проекта, имени клиента. Синтетика, узнаваемо синтетическая: `Musterquartier`, `Beispielstraße`, `M. Musterfrau`.
- **R-25 в силе для ставок:** ставки и множители берутся из каталога `calculation-spec.md`; выводить новые нельзя. Если профиль требует множителя, которого в каталоге нет, — назови это в отчёте, а не придумывай (`D-22` разрешает выведенные величины только с пометкой ⚙ и провенансом).
- Числа в немецком формате, U+202F между числом и единицей.
