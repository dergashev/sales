## Почему 36 мутаций прошли и как закрыть классы

### Пороговые значения контраста — T01, T02, T03

- **T01:** `tools/verify.py:887-889` удаляет из `claims` любое `3:1`, если на строке есть слово о пороге/прохождении. Поэтому заведомо ложное измерение для пары с фактическими 2,60:1 вообще не доходит до `colors_on()` и формулы. Исправление: не исключать число по значению; отдельно парсить нормативное неравенство (`≥ 3:1`) и измеренное равенство, а при названной паре всегда пересчитывать фактический ratio.
- **T02:** та же ветка безусловно отбрасывает `4,5:1`; фактические 3,10:1 не сравниваются. Исправление то же, плюс тест на точную границу normal text.
- **T03:** та же ветка отбрасывает `7:1`; фактические 4,79:1 не сравниваются. Исправление то же, плюс тест на точную границу AAA. Контроль T38 показывает, что соседнее `3,01:1` формула уже ловит: слепота создана ровно строками 887–889.

### CSS разбирается не как CSS — T05–T10, T13, T14, T35, T36

- **T05:** `tools/verify.py:999-1006` проверяет только наличие подстроки `var(--size-hit-target-default)` в значении width/height. Арифметика вокруг `var()` не вычисляется. Исправление: требовать значение, эквивалентное ровно токену без уменьшающих операций, либо вычислять CSS expression и проверять минимум 44 px.
- **T06:** `tools/verify.py:679-681` доказывает только наличие хотя бы одного объявления 1200 px. Эффективное последнее объявление и дубли не проверяются. Исправление: парсить каскад/блок `:root`, запрещать дубли канонических custom properties и сверять эффективное значение.
- **T07:** `LAYOUT-003` смотрит только на custom property и две текстовые строки README/screen-map; обычный `max-width` отсутствует в области проверки. Исправление: проверять все применяемые `width`/`max-width` для контейнеров и запрещать обход токена.
- **T08:** `tools/verify.py:796-801` извлекает только числа с суффиксом `px`; `rem`, `em`, `calc()` и CSS variables вне шкалы не классифицируются. Исправление: CSS value parser + нормализация абсолютных единиц; для прочих единиц требовать санкционированный semantic token.
- **T09:** `tools/verify.py:773-786` режет CSS по строкам, после чего regex `border-radius` ожидает значение на той же строке. Исправление: разбирать декларации из CSS AST, а не строки.
- **T10:** `tools/verify.py:789-795` знает только `box-shadow` и `text-shadow`; визуально та же тень через `filter: drop-shadow()` не относится к классу. Исправление: единый запрет shadow effects, включая filter/SVG filter.

## Классы дефектов, которых инструмент не умеет видеть

1. **Эффективная семантика CSS.** Нет AST, каскада, раскрытия shorthand/`calc()`, нормализации единиц и анализа альтернативных свойств с тем же визуальным эффектом.
2. **Семантическая роль токена в месте применения.** Инструмент умеет подтвердить правильное объявление token, но не что token применён только к разрешённому компоненту, свойству, состоянию и подложке.
3. **Полнота primitive-контрактов.** Для `components-core.md` нет проверки семи осей, keyboard/screen-reader/touch/reduced-motion, ARIA, reflow и обязательных тестовых разделов.
4. **Семантика state machine и порядок приоритетов.** Наличие имён проверяется местами; разрешённые переходы и precedence delivery/quote/normalization не моделируются.
5. **Содержание табличного условия.** `OUT-SEND` доказывает «шесть строк», но не что каждая строка содержит требуемый предикат.
6. **Истинность инвариантов data-model.** `DM-INVARIANT` — coverage по идентификаторам, а не проверка формул, знаков, единиц, tax basis или порядка.
7. **Согласованность дублированных нормативных утверждений.** Правильная копия в инварианте маскирует противоположное определение в основном разделе того же файла или в CLAUDE/README.
8. **Семантика отрицания.** `не`, `никогда`, `запрещён` → противоположное утверждение обычно проходит, если строка не входит в шесть специально зафиксированных фраз `check_governance()`.
9. **Содержательность причины.** Длина `notApplicableReason` принимается за доказательство причины.
10. **Изоляция зависимых проверок.** Один неприменившийся parser обрывает весь арифметический pipeline, поэтому независимые downstream-классы не получают данных и не могут отличить дефект документа от дефекта проверяльщика.

## Ложные срабатывания и недостоверный selftest

### 1. Корректный контрольный пример R-01 объявлен вакуумом

`docs/product/calculation-spec.md:226` содержит воспроизводимую формулу: точное значение `3.681.809,272225`, отображение `≈ 3.682.000 €`; региональный эффект `294.544,741778` отображается `≈ +295.000 €`. Regex `tools/verify.py:2642-2644` требует старую форму `= **<число> €` и не допускает вставку «точно …, показ **≈ …». Это корректная содержательная правка, но гейт выдаёт новый `CALC-SPEC [вакуум]`.

### 2. Один parser failure порождает два обвинения корректных файлов

`tools/verify.py:2375-2379` ловит `Vacuum` вокруг **всей** `_arithmetic()` и прекращает её. Публикация `self.fx` находится только в `tools/verify.py:2658-2694`, поэтому после ошибки позднего R-01 она не выполняется. Затем `tools/verify.py:2173` и `tools/verify.py:1605` регистрируют `OUT-MONEY` и `RM-FIXTURE` «величины фикстуры не вычислены», хотя эти файлы не портили. Это два производных ложных срабатывания и потеря независимой проверки.

### 3. Негативные мутации selftest сравниваются с грязной базой

`tools/verify.py:3277-3280` фиксирует ошибку базы, но продолжает все случаи. Для негативной мутации `tools/verify.py:3308-3311` считает ложным срабатыванием **любой** `got_new`, а не дельту к `v0.new`. Поэтому безопасные RFC 2606-примеры и корректный label `Anteil an Zwischensumme` ошибочно обвинены базовыми `NBSP/CALC-SPEC/OUT-MONEY/RM-FIXTURE`. Итог `133/144` смешивает живость детекторов, неприменимые mutations и грязную базу и не является доказательством 133 работающих случаев.

Два базовых `NBSP` здесь ложными не считаю: правило U+202F сформулировано явно, а найденные строки действительно содержат U+0020.
